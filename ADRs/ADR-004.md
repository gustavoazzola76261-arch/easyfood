# ADR-004 — Arquitetura em camadas

## Status

Aceita

## Data

3/09/2026

## Responsável

Gustavo de Carvalho

## Contexto

Após a introdução do SQLAlchemy, o `server.py` acumulava várias responsabilidades: subir o Flask, validar entrada, acessar o banco e ligar o servidor. Precisamos reorganizar a aplicação **sem mudar o comportamento externo** (`GET`/`POST /restaurants`).

## Alternativas consideradas

1. Manter tudo em `server.py`
2. Separar apenas models/utils
3. Arquitetura em camadas (routes → controller → service → database)
4. Microserviços por domínio

## Decisão

Adotar **arquitetura em camadas** dentro de um monólito modular:

```
server.py          → liga o servidor + init do banco
src/app.py         → configura a aplicação Flask
routes             → caminhos HTTP
controller         → req/res e validação de entrada
service            → regras e operações (sem Flask)
database           → engine, sessão e models
```

## Justificativa

- Cada camada tem uma responsabilidade clara (Single Responsibility).
- O Service não depende de `request`/`response`, facilitando testes e reuso.
- Refatoração segura: contrato HTTP permanece idêntico.

## Consequências

### Positivas

- Manutenção e leitura melhores conforme o sistema cresce.
- Fronteiras claras para novos módulos.
- Facilita revisão de código e ADRs futuros.

### Negativas / trade-offs

- Mais arquivos e indireção
- Risco de “pass-through” excessivo se camadas não agregarem valor.

## Critérios de revisão

Reavaliar quando:

1. Domínios crescerem a ponto de exigir bounded contexts / serviços separados.
2. Surgir necessidade de CQRS, eventos ou filas.
3. Testes unitários do Service mostrarem acoplamento indesejado ao ORM.
