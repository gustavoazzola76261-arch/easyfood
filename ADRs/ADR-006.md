# ADR-006 — Integração do frontend com a API Python

## Status

Aceita

## Data

17/09/2026

## Responsável

Gustavo de Carvalho

## Contexto

O frontend `index.html` (mockup mobile da EasyFood) já consumia `http://localhost:3000/restaurants`. Com a API em Python evoluída até JWT, faltava:

1. Servir o HTML pelo mesmo processo Flask (ou garantir CORS).
2. Adaptar o cadastro ao `POST /restaurants` protegido.
3. Orientar o usuário a subir o backend com `python server.py`.

## Alternativas consideradas

1. Abrir o HTML via `file://` e só usar CORS
2. Servidor estático separado (Live Server) + API
3. Flask servindo `public/index.html` + API no mesmo host/porta
4. SPA com build (React/Vue)

## Decisão

- Mover o frontend para `public/index.html`
- Servir arquivos estáticos e a rota `/` pelo Flask
- Manter CORS habilitado para flexibilidade em testes
- Incluir login/registro no fluxo de cadastro, persistindo o JWT em `localStorage`

## Justificativa

- Um único comando (`python server.py`) sobe API + UI na porta 3000.
- Reduz atrito para demonstração em aula e para o professor validar o MVP.
- Mantém o visual original do mockup, apenas evoluindo o que a arquitetura passou a exigir (auth).
- Evita complexidade de bundlers nesta disciplina.

## Consequências

### Positivas

- Experiência completa: listar, autenticar e cadastrar.
- Contrato HTTP estável e documentado nos ADRs anteriores.
- Frontend e backend versionados juntos no histórico git da evolução.

### Negativas / trade-offs

- UI de auth é mínima (sem tela de perfil completa).
- Token no `localStorage` é conveniente, porém vulnerável a XSS (aceitável no escopo acadêmico).
- Monólito continua servindo estáticos; em produção costuma-se separar CDN/nginx.

## Critérios de revisão

Reavaliar quando:

1. O frontend crescer para múltiplas páginas/rotas client-side.
2. Houver requisito de refresh token / logout seguro.
3. O deploy separar API e assets em containers distintos.
