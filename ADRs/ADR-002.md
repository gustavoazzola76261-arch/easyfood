# ADR-002 — Armazenar restaurantes em memória

## Status

Aceita (temporária)

## Data

27/08/2026

## Responsável

Gustavo de Carvalho

## Contexto

O Product Owner solicitou que restaurantes também possam se cadastrar na EasyFood. A API passou a expor:

- `GET /restaurants` — listar
- `POST /restaurants` — cadastrar

O produto ainda está em prototipação. A prioridade é validar o fluxo de ponta a ponta com o frontend antes de introduzir infraestrutura de banco.

## Alternativas consideradas

1. Lista/dicionário em memória (Python)
2. PostgreSQL
3. MongoDB
4. SQLite
5. Arquivo JSON
6. Firebase

## Decisão

Manter os restaurantes em uma **lista em memória** no processo da aplicação Flask.

## Justificativa

- Velocidade máxima para implementar e demonstrar o novo requisito.
- Sem instalação de banco, migrations ou ORM nesta etapa.
- Suficiente para validar contrato HTTP (`201 Created`, validação de nome/categoria).

## Consequências

### Positivas

- Desenvolvimento e testes locais imediatos.
- Complexidade mínima no `server.py`.
- Facilita comparar, depois, o impacto de introduzir persistência.

### Negativas / trade-offs

- Dados somem ao reiniciar o servidor (`Ctrl+C` / novo processo).
- Não escala para múltiplas instâncias.
- Sem integridade, backups ou consultas avançadas.

## Critérios de revisão

Reavaliar quando:

1. For necessário manter dados entre reinícios e deploys.
2. O MVP for validado para produção.
3. Surgirem relacionamentos entre entidades (ex.: usuários × restaurantes).
4. O volume de dados deixar de caber razoavelmente em memória.
