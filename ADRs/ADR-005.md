# ADR-005 — Autenticação com JWT

## Status

Aceita

## Data

10/09/2026

## Responsável

Gustavo de Carvalho

## Contexto

Com a EasyFood organizada em camadas e com persistência, o próximo requisito é autenticar usuários e proteger o cadastro de restaurantes. Endpoints previstos:

- `POST /auth/register`
- `POST /auth/login`
- `GET /auth/me` (protegido)
- `POST /restaurants` (protegido)
- `GET /restaurants` (público)

## Alternativas consideradas

1. JWT emitido pela própria API (stateless)
2. Sessões server-side (cookies)
3. AWS Cognito / Identity Provider externo
4. OAuth login com Google

## Decisão

Implementar **JWT próprio** com:

- `bcrypt` para hash de senhas
- `PyJWT` para assinar/verificar tokens (`HS256`, expiração 1 dia)
- `JWT_SECRET` via `.env` (nunca hardcoded no código de produção)
- Middleware `authenticate` reutilizável nas rotas protegidas

## Justificativa

- Adequado ao contexto acadêmico e ao monólito atual (baixa complexidade operacional).
- Stateless: facilita testes e o fluxo Bearer Token do Postman/frontend.
- Mantém o domínio `auth/` simétrico ao módulo `restaurants/` (service/controller/routes).
- Cognito/Google seriam over-engineering nesta fase e acoplariam a provedores externos.

## Consequências

### Positivas

- Senhas nunca retornadas e armazenadas apenas como hash.
- Controle fino: leitura pública, escrita autenticada.
- Base pronta para papéis/autorização futura.

### Negativas / trade-offs

- Revogação de tokens exige estratégia adicional (blacklist/curta expiração/refresh).
- Segredo compartilhado (`JWT_SECRET`) precisa de gestão cuidadosa.
- Frontend precisará enviar `Authorization: Bearer <token>` no POST.

## Critérios de revisão

Reavaliar quando:

1. Houver requisito de SSO corporativo ou login social.
2. Precisarmos revogar sessões imediatamente (logout global).
3. Múltiplos serviços precisarem validar identidade (API gateway / IdP).
